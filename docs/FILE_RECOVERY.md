# 附件存储与恢复边界

当前实现选择共享文件系统：所有 Chat 节点需要使用同一 MySQL、同一附件目录和相同主密钥。Compose 的命名卷仅覆盖同一 Docker 宿主机，不自动提供跨机器共享。跨主机部署必须另行挂载共享存储，并实测该存储的跨客户端文件锁与同步写入语义；各节点独立本地目录不满足要求。

## 提交顺序

1. 创建上传文件及随机 nonce 前缀，完成系统同步，再创建数据库元数据。Linux 同步父目录条目。
2. 持有附件锁，验证目标偏移之前的完整分片。已有目标分片只允许内容完全相同的重试，不覆盖、不截断后续分片。
3. 新分片写入并关闭文件流，执行 Windows FlushFileBuffers 或 POSIX fsync，随后提交数据库 offset CAS。
4. 数据库更新失败时保留文件。重新发起续传查询最新 offset；相同分片重复提交不会更改密文。
5. 上传完成后核对摘要，再标记为可下载。

现有 CHATFILE1 格式继续可读。目标分片发生部分写入或内容冲突时不能覆盖同一 nonce：本次请求失败，需取消旧上传并使用新 ID 上传。已确认分片缺失也会失败，不通过扩展文件填零来伪造恢复。

## 尚需验收

- 在两台主机上并发重试同一个上传 ID，确认文件锁生效、失败 CAS 不删除其他节点的数据。
- 在密文同步之前、同步之后和数据库提交返回之前分别终止进程，核对 offset、内容与摘要。
- 真实掉电、存储控制器缓存、共享文件系统故障与 Windows 目录条目的持久性无法由单元测试证明。
- 数据库与附件目录需作为同一恢复点备份；主密钥应单独保管。只恢复其中一部分可能留下缺失文件或孤立密文。

本机测试覆盖相同偏移重试、内容冲突、后续分片保留和截断记录拒绝；两个存储实例的测试不能替代跨机器验收。生产对象存储适配、自动孤立文件核对和全局配额仍属后续工作。
